# v1 통합 실패 분석

## 작성 목적

이 문서는 v1을 실패한 결과물로 단정하기 위한 문서가 아닙니다. 로컬 v1 코드에서 확인한 통합 위험을 근거로 남기고, v2에서 같은 문제가 반복되지 않도록 개선 방법과 검증 기준을 정의합니다.

## v1에서 확인한 구조

- 백엔드: Java 17, Spring Boot, JPA, Spring Security, JWT
- 프론트엔드: React와 JavaScript
- 데이터베이스 스키마: Hibernate `ddl-auto=update`
- API 호출: Axios와 Fetch를 각 화면에서 직접 사용
- 일부 화면 데이터: 프론트엔드의 JSON 파일 및 별도 로컬 서버 사용

## 문제 1. 요청 필드가 코드 사이에서 수동으로 연결됨

v1 회원가입 백엔드 DTO는 다음 필드를 요구합니다.

```text
studentNumber
userName
email
password
passwordCheck
```

프론트엔드에서는 화면 상태의 `name`, `confirmPassword` 등을 요청 직전에 `userName`, `passwordCheck`로 직접 변환합니다. 로그인 화면에서도 `student_number`를 `studentNumber`로 바꾸어 전송합니다.

이 방식은 동작할 수 있지만 백엔드 DTO가 변경되어도 프론트엔드 빌드에서 오류가 발생하지 않습니다. 주석과 개발자의 기억에 의존하기 때문에 필드 누락이나 이름 불일치가 실제 HTTP 요청 시점에 발견될 수 있습니다.

### v2 개선 방향

- 요청과 응답을 DTO로 명확하게 정의
- DTO validation으로 서버 경계에서 잘못된 요청 차단
- OpenAPI 문서를 생성하고 프론트엔드 TypeScript 타입으로 변환
- API 계약 변경 여부를 CI에서 검사

## 문제 2. API 주소와 데이터 출처가 분산됨

v1 프론트엔드에서 확인한 호출 주소에는 다음 형태가 함께 존재합니다.

```text
http://localhost:8080
http://localhost:3001
http://localhost:3002
상대경로 요청
```

실제 Spring Boot API, 별도 JSON 서버, 프론트엔드의 정적 JSON 파일이 화면별로 혼합되어 있습니다. 따라서 특정 화면이 실제 백엔드와 연결되었는지, mock 데이터를 사용하는지 코드를 추적해야 알 수 있습니다.

### v2 개선 방향

- API 호출을 별도 모듈로 분리
- 환경변수로 API 기준 주소를 한 곳에서 관리
- 실제 API와 mock 데이터를 명확하게 구분
- 회원가입부터 내 정보 조회까지 실제 HTTP 흐름을 먼저 관통

## 문제 3. DB 변경 이력을 재현하기 어려움

v1은 다음 설정으로 Entity 변경을 DB에 반영합니다.

```properties
spring.jpa.hibernate.ddl-auto=update
```

개발 중에는 편리하지만 어떤 SQL이 어떤 순서로 적용되었는지 저장소에 이력이 남지 않습니다. 팀원의 기존 DB 상태에 따라 결과가 달라질 수 있고, 깨끗한 DB에서 같은 구조를 재현했는지 검증하기 어렵습니다.

### v2 개선 방향

- 운영 스키마 변경은 Flyway SQL로 관리
- JPA는 `ddl-auto=validate`로 Entity와 테이블의 일치 여부만 확인
- CI에서도 빈 MySQL에 Flyway를 적용한 뒤 테스트

## 문제 4. 오류 처리 책임이 분산됨

v1에는 전역 예외 처리기가 있지만 일부 Controller에서도 `try-catch`로 예외를 직접 HTTP 응답으로 변환합니다. 같은 종류의 오류가 API마다 다른 상태 코드와 응답 형태로 반환될 가능성이 있습니다.

### v2 개선 방향

- Service는 업무 예외를 발생시킴
- `@RestControllerAdvice`가 예외를 한 곳에서 HTTP 응답으로 변환
- 성공과 실패 응답 형식을 일관되게 유지
- `400`, `401`, `403`, `409` 상황을 테스트로 고정

## 문제 5. 단위 기능 구현과 실제 통합 성공이 구분되지 않음

Controller, Service, JWT, 화면이 각각 존재하는 것만으로 전체 사용자 흐름이 성공했다고 볼 수 없습니다. 실제 브라우저에서 사용하는 요청 필드, 인증 헤더, 데이터베이스 상태까지 함께 검증해야 합니다.

### v2 개선 방향

다음 관통 흐름을 단계별 완료 기준으로 사용합니다.

```text
회원가입
→ 로그인
→ JWT 저장
→ 인증 헤더 전송
→ 내 정보 조회
→ 화면 표시
```

각 단계는 빌드 성공뿐 아니라 실제 HTTP 응답과 DB 상태까지 확인합니다.

## v2 검증 기준

- Flyway 이력으로 빈 DB를 재생성할 수 있는가
- 백엔드와 프론트엔드가 각각 독립적으로 빌드되는가
- API 입력 오류가 정해진 상태 코드로 반환되는가
- 인증이 없거나 JWT가 잘못되었을 때 `401`이 반환되는가
- OpenAPI 계약 변경 시 프론트엔드 타입 또는 CI가 불일치를 발견하는가
- 동시 승인 요청에서도 정원과 멤버 수가 일치하는가

측정하거나 검증하지 않은 항목은 완료된 결과로 기록하지 않습니다.
